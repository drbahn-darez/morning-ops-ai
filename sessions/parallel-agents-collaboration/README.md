# 병렬 작업과 에이전트 협업으로 퀄리티 올리기

> 부스트캠프 세션 자료 (초안 v0.1)
> 소요 시간: 90분 (강의 45분 + 핸즈온 35분 + Q&A 10분)

---

## 1. 세션 개요

### 한 줄 요약
"AI에게 일을 시키는 것"에서 한 단계 나아가, **여러 에이전트를 병렬로 굴리고 서로 검증하게 만들어서** 결과물의 속도와 품질을 동시에 끌어올리는 방법을 배웁니다.

### 학습 목표
이 세션이 끝나면 다음을 할 수 있습니다.

1. 하나의 작업을 **병렬화 가능한 단위로 분해**할 수 있다.
2. 서브에이전트(subagent)를 활용해 **탐색·구현·검증을 동시에** 진행할 수 있다.
3. "생성하는 에이전트"와 "검증하는 에이전트"를 분리하는 **적대적 검증(adversarial verification)** 패턴을 적용할 수 있다.
4. git worktree 등을 활용해 **여러 에이전트가 충돌 없이 같은 저장소를 수정**하게 할 수 있다.

### 대상
- Claude Code(또는 유사 AI 코딩 도구)를 단일 세션으로 써본 경험이 있는 분
- "AI가 만든 결과물을 매번 내가 다 검토해야 해서 오히려 느리다"고 느껴본 분

## 2. 왜 병렬·협업인가? (10분)

### 2.1 단일 에이전트의 한계

| 한계 | 증상 |
|------|------|
| 컨텍스트 한계 | 큰 코드베이스를 한 번에 다 못 읽음. 뒤로 갈수록 앞의 내용을 잊음 |
| 순차 처리 | 파일 10개를 고치면 10배의 시간이 걸림 |
| 자기 검증의 맹점 | 자기가 쓴 코드는 자기가 봐도 맞아 보임 (사람과 똑같음) |
| 관점의 단일성 | 한 프롬프트 = 한 관점. 보안·성능·정합성을 동시에 보기 어려움 |

핵심 통찰: **이 한계들은 "더 좋은 프롬프트"로 해결되지 않습니다.** 구조로 해결해야 합니다.

### 2.2 병렬화가 주는 것 — 속도만이 아니다

- **속도**: 독립적인 작업 N개를 동시에 → 벽시계 시간은 가장 느린 하나만큼만
- **커버리지**: 같은 질문을 서로 다른 각도에서 동시에 탐색 (파일명으로, 내용으로, 히스토리로…)
- **품질**: 독립된 에이전트끼리 교차 검증 → 그럴듯하지만 틀린 답이 걸러짐

> 💡 비유: 코드 리뷰를 작성자 본인이 하는 회사 vs. 독립된 리뷰어가 하는 회사.
> 에이전트도 똑같습니다. **만든 놈이 검사하면 안 됩니다.**

## 3. 핵심 개념 4가지 (15분)

### 3.1 병렬 도구 호출 (Parallel Tool Calls)

가장 낮은 수준의 병렬화. 서로 의존성이 없는 읽기/검색은 한 번에 요청합니다.

```
❌ "A 파일 읽어줘" → (대기) → "B 파일도 읽어줘" → (대기) → "C도…"
✅ "A, B, C 파일을 읽고 세 파일의 공통 패턴을 정리해줘"
```

에이전트 입장에서 독립적인 호출은 동시에 실행됩니다. 사용자가 할 일은 **의존성 없는 요청을 묶어서 한 번에 던지는 것**뿐입니다.

### 3.2 서브에이전트 (Subagents / Fan-out)

메인 에이전트가 하위 에이전트를 여러 개 띄워 작업을 위임하는 구조.

```
메인 에이전트 (오케스트레이터)
├── 탐색 에이전트: "인증 로직이 어디 있는지 찾아와"
├── 탐색 에이전트: "API 에러 핸들링 패턴을 조사해와"
└── 탐색 에이전트: "테스트 커버리지 현황을 파악해와"
        ↓ (결과만 수집)
메인 에이전트: 종합해서 구현 계획 수립
```

**왜 좋은가:**
- 각 서브에이전트는 자기만의 깨끗한 컨텍스트를 가짐 → 메인의 컨텍스트를 오염시키지 않음
- 파일 수십 개를 뒤지는 지저분한 과정은 서브에서 소화하고, **결론만** 메인으로 올라옴
- 서로 독립이면 동시에 실행됨

**프롬프트 예시:**
```
이 리팩토링을 시작하기 전에 서브에이전트 3개를 병렬로 띄워서
(1) 이 함수를 호출하는 모든 위치, (2) 관련 테스트 파일,
(3) 비슷한 리팩토링을 했던 과거 커밋을 각각 조사하게 해줘.
```

### 3.3 역할 분리와 적대적 검증 (Adversarial Verification)

이 세션의 핵심입니다. **생성과 검증을 다른 에이전트에게 맡깁니다.**

```
[생성자] 코드 작성 / 버그 후보 발견 / 문서 초안
    ↓
[검증자 N명] "이 주장을 반박해봐. 확신이 없으면 기각해."
    ↓
[판정] 과반이 살아남은 것만 채택
```

**왜 "반박해봐"라고 시키는가?**
- "검토해줘"라고 하면 에이전트는 동조하는 경향이 있음 (사람의 확증 편향과 유사)
- "틀렸다는 증거를 찾아봐"라고 명시적으로 시키면 훨씬 날카로워짐

**관점 다양화(perspective-diverse) 변형:**
동일한 반박자 3명 대신, 서로 다른 렌즈를 부여합니다.
- 검증자 A: 정합성(correctness) 관점 — 로직이 실제로 맞는가?
- 검증자 B: 보안 관점 — 악용 가능한 입력이 있는가?
- 검증자 C: 재현성 관점 — 실제로 그 버그가 재현되는가?

같은 실수를 3번 반복하는 것(중복)보다, 서로 다른 실패 모드를 잡는 것(다양성)이 강합니다.

### 3.4 작업 공간 격리 (Isolation — git worktree)

여러 에이전트가 **동시에 파일을 수정**하면 서로 덮어씁니다. 해결책은 격리된 작업 공간.

```
repo/
├── main 작업 트리          ← 메인 에이전트
├── worktree-agent-1/       ← 마이그레이션 담당
├── worktree-agent-2/       ← 테스트 수정 담당
└── worktree-agent-3/       ← 문서 갱신 담당
```

- 읽기 전용 작업(탐색·조사·리뷰)은 격리가 **불필요** — 그냥 병렬로 돌리면 됨
- 쓰기 작업이 병렬일 때만 worktree를 사용 (격리 자체도 비용이므로)
- 각자 브랜치에서 작업 → 마지막에 병합

## 4. 실전 패턴 카탈로그 (10분)

현업에서 바로 쓸 수 있는 조합 패턴들입니다.

### 패턴 1: 탐색 팬아웃 (Understand)
> "이 코드베이스 파악해줘"를 제대로 하는 법

```
서브에이전트 N개가 서브시스템별로 병렬 조사
→ 각자 구조화된 요약 반환
→ 메인이 하나의 지도로 종합
```
쓰는 순간: 온보딩, 큰 리팩토링 전 사전 조사, 레거시 분석

### 패턴 2: 심사위원단 (Judge Panel)
> 설계 결정을 한 번의 시도로 끝내지 않는 법

```
서로 다른 접근으로 N개의 독립 설계안 생성
  (예: MVP 우선 / 리스크 우선 / 사용자 경험 우선)
→ 심사 에이전트들이 채점
→ 1등 안을 기반으로, 나머지 안의 좋은 아이디어를 이식해 종합
```
쓰는 순간: 아키텍처 결정, API 설계, 해법이 여러 개인 문제

### 패턴 3: 찾고-검증하기 (Find → Verify)
> 코드 리뷰/버그 헌팅의 품질을 올리는 법

```
차원별 리뷰어 병렬 실행 (버그 / 성능 / 보안 / 테스트 커버리지)
→ 발견 사항마다 독립 검증자가 적대적 검증
→ 확인된(confirmed) 것만 보고
```
쓰는 순간: PR 리뷰, 배포 전 점검, "그럴듯한 오탐"에 지쳤을 때

### 패턴 4: 마를 때까지 반복 (Loop-until-dry)
> "버그 10개 찾아줘"가 아니라 "다 찾아줘"를 하는 법

```
라운드마다 새 발견자들을 투입
→ 새로운 발견이 없는 라운드가 2번 연속되면 종료
```
쓰는 순간: 크기를 미리 알 수 없는 탐색 (버그, 엣지 케이스, 마이그레이션 대상)

### 패턴 5: 대규모 마이그레이션 (Discover → Transform → Verify)
```
대상 지점 발견 (병렬 탐색)
→ 지점별로 에이전트가 각자 worktree에서 변환
→ 변환 결과를 별도 에이전트가 검증
```
쓰는 순간: API 교체, 프레임워크 업그레이드, 전 파일 일괄 수정

### 안티패턴 ⚠️
| 안티패턴 | 왜 문제인가 |
|----------|-------------|
| 모든 걸 병렬화 | 의존성 있는 작업을 병렬화하면 오히려 재작업 발생. 순차가 맞는 건 순차로 |
| 불필요한 배리어(barrier) | "1단계 전부 끝나야 2단계 시작"을 남발하면 빠른 작업이 느린 작업을 기다리며 놀게 됨. 항목별 파이프라인이 기본 |
| 검증 없는 팬아웃 | 에이전트 10개가 만든 결과를 그대로 합치면 오류도 10배. 반드시 검증 단계를 붙일 것 |
| 만든 에이전트에게 검증 맡기기 | 자기 답을 자기가 채점 → 무의미. 검증자는 반드시 독립 컨텍스트로 |
| 결과 무한 신뢰 | 다수결로 살아남았어도 최종 책임은 사람. 특히 프로덕션 반영 전엔 직접 확인 |

## 5. 라이브 데모 시나리오 (10분)

강의 중 실제로 시연할 시나리오입니다. (데모 환경: 적당한 크기의 오픈소스 저장소 또는 팀 내부 저장소)

### 데모 A: 순차 vs 병렬 체감 비교 (5분)
1. 같은 조사 과제를 **단일 에이전트 순차 방식**으로 요청 → 소요 시간 기록
2. 동일 과제를 **서브에이전트 3개 병렬**로 요청 → 시간 + 결과 품질 비교
3. 포인트: 시간 단축뿐 아니라, 각 서브에이전트의 요약 품질이 더 좋다는 것 (컨텍스트가 깨끗해서)

### 데모 B: 적대적 검증으로 오탐 걸러내기 (5분)
1. "이 코드에서 버그를 찾아줘" → 발견 사항 목록 확보 (보통 오탐 섞임)
2. 발견 사항마다 "이 주장을 반박해봐" 검증자 투입
3. 기각된 항목과 살아남은 항목을 비교하며, 검증 전 목록을 그대로 믿었다면 어떤 낭비가 생겼을지 확인

## 6. 핸즈온 실습 (35분)

### 실습 준비
- 각자 Claude Code 세션 + 실습용 저장소 (사전 안내한 저장소 clone)
- 페어로 진행 권장 (한 명은 프롬프트, 한 명은 결과 관찰·기록)

### 실습 1: 병렬 탐색 (10분) — 난이도 ★
실습용 저장소에 대해 다음을 요청해보세요.

```
서브에이전트 3개를 병렬로 띄워서 이 저장소를 조사해줘.
(1) 전체 디렉터리 구조와 각 모듈의 책임
(2) 외부 의존성과 그 용도
(3) 테스트 구조와 실행 방법
각 에이전트의 결과를 종합해서 신규 입사자용 온보딩 문서 한 페이지로 정리해줘.
```

**체크포인트**: 서브에이전트들이 실제로 동시에 도는지, 최종 종합 품질이 어떤지 관찰

### 실습 2: 생성-검증 분리 (15분) — 난이도 ★★
1단계 — 생성:
```
이 저장소에서 잠재적 버그를 5개 찾아줘. 각각 파일 위치와 근거를 명시해줘.
```
2단계 — 적대적 검증:
```
방금 찾은 버그 후보 각각에 대해 독립 서브에이전트를 띄워서
"이 주장이 틀렸다는 증거"를 찾게 해줘. 반박에 성공하면 후보에서 제외하고,
살아남은 것만 확신도와 함께 다시 보고해줘.
```

**체크포인트**: 5개 중 몇 개가 살아남았나요? 기각된 항목의 기각 사유를 읽어보세요. 이게 여러분이 아낀 검토 시간입니다.

### 실습 3 (심화): 병렬 수정 (10분) — 난이도 ★★★
```
이 저장소의 (사전 지정된 간단한 일괄 수정 과제, 예: deprecated API 3곳 교체)를
worktree로 격리된 에이전트들이 병렬로 수정하게 하고,
각 수정에 대해 검증 에이전트가 테스트를 돌려 확인한 뒤 병합해줘.
```

**체크포인트**: 충돌 없이 병합됐는지, 검증 단계에서 걸린 문제가 있었는지

### 실습 회고 질문 (조별 공유)
1. 병렬화했더니 오히려 안 좋았던 지점이 있었나요? 왜였을까요?
2. 검증자가 기각한 것 중 "사람인 나도 속을 뻔한" 항목이 있었나요?
3. 내 실제 업무에서 이번 주에 바로 적용할 수 있는 패턴은 무엇인가요?

## 7. 정리 & 핵심 메시지 (5분)

1. **병렬화는 속도가 아니라 구조의 문제다** — 의존성 없는 작업을 묶는 눈을 기르자.
2. **만든 에이전트가 검증하게 하지 마라** — 생성과 검증의 분리가 품질의 시작.
3. **"검토해줘" 대신 "반박해봐"** — 적대적 프롬프트가 오탐을 거른다.
4. **다양성 > 중복** — 같은 검증자 3명보다 다른 관점 3명.
5. **마지막 책임은 사람** — 에이전트 협업은 검토 비용을 줄여주는 것이지, 없애주는 것이 아니다.

## 부록 B. 자주 나오는 질문 (FAQ)

**Q. 병렬로 돌리면 비용(토큰)이 많이 들지 않나요?**
A. 총 토큰은 늘어납니다. 하지만 (1) 서브에이전트의 지저분한 탐색 과정이 메인 컨텍스트를 차지하지 않아 메인 세션의 수명이 길어지고, (2) 오탐 검토에 쓰는 사람의 시간이 줄어듭니다. "토큰 비용 vs 내 시간"으로 계산하면 대부분 남는 장사입니다. 다만 간단한 단건 조회까지 팬아웃하는 것은 낭비입니다.

**Q. 서브에이전트가 몇 개까지가 적당한가요?**
A. 작업의 독립성이 기준입니다. 자연스럽게 쪼개지는 단위(서브시스템, 파일 그룹, 관점)만큼만. 억지로 쪼개면 서로 겹치는 조사를 하며 낭비가 생깁니다. 검증자는 3명(2/3 다수결)이 실용적인 출발점입니다.

**Q. 에이전트끼리 결과가 충돌하면요?**
A. 그게 바로 신호입니다. 충돌하는 지점 = 사람이 직접 봐야 하는 지점. 협업 구조는 "어디를 봐야 하는지"를 좁혀주는 장치이기도 합니다.
